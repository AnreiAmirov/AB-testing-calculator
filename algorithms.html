How to solve a problem at an interview

Interviewers rarely judge only whether you reach the answer. They watch how you think: whether you clarify the task, start from something that works, and improve it deliberately. Silence for ten minutes followed by perfect code scores worse than reasoning aloud and arriving at a good solution. Six steps make that process visible.

  1. ClarifyRestate the task in your own words. Ask about the edges: can the array be empty? Are there negatives or duplicates? Is the input sorted? Each answer can change the solution.
  2. Work an example by handTake a small input and solve it on paper. This is where you notice the pattern — and catch a misunderstanding before writing a line of code.
  3. Say the brute forceDescribe the obvious solution and its complexity, even if it is slow. It proves you understand the task and gives a baseline to improve on.
  4. Find the bottleneckAsk what work is repeated. Usually it is a nested loop re-scanning data you have already seen — the classic place where a dictionary, two pointers or a running sum helps.
  5. Write the codeClear names, small steps, comments where intent is not obvious. Readable code is part of the grade, not decoration.
  6. Test it yourselfWalk through your example line by line, then the edges: empty input, one element, all equal values. Finding your own bug is a plus; the interviewer finding it is a minus.
The most common mistake is jumping straight to code. Two minutes spent clarifying and working an example save twenty minutes of rewriting a solution to the wrong problem.
The logic behind the solution

Knowing the code by heart does not help when the task is worded slightly differently. What transfers is the reasoning. Three topics come up at almost every analyst interview — strings and counting, sorting, and two pointers — so here they are taken apart slowly, with the questions you should be asking yourself at each step.

Four questions that start almost any solution
  1. Does order matter? "Count the letters" and "count letters in a row" are different tasks.
  2. What must I remember while walking through the data? A counter, the previous element, the best value so far, what I have already seen.
  3. When does what I remember change? This moment — "the run broke", "the sum got too big" — is the heart of the algorithm.
  4. What is left over at the end? Many bugs live here: the last group is never written because the loop ended first.

1 · Strings and counting characters

A string is a sequence of characters, just like a list. You can loop over it, take s[i] by position and look back at the previous character with s[i - 1]. One difference matters: strings cannot be changed in place. So the result is collected in a list and glued together once at the end with "".join(parts).

The classic task: count every character

The most frequent string problem at analyst interviews: print how many times each character appears, as "count + character". The count is the total for the whole string, so abab gives 2a2b — the two a's are counted together even though they are not neighbours. Characters go in the order they first appear.

Given

→
Answer

How to reason about it
  1. Order of neighbours does not matter — only "how many of each". So we need a place to keep a running tally per character: a dictionary character → count.
  2. Walk through the string once. For each character: take its current count, or 0 if it is new, and add one — counts.get(ch, 0) + 1.
  3. A dictionary remembers the order in which keys were first added (Python 3.7+). So walking through it gives the characters in order of first appearance — no extra work needed.
  4. Build the answer from the dictionary: for every pair write "count + character" and join.

def count_chars(s):
    """'aabbccc' -> '2a2b3c', 'abab' -> '2a2b': how many times each char appears
    in total, in the order chars first appear."""
    counts = {}                       # a dict remembers insertion order (Python 3.7+)
    for ch in s:
        counts[ch] = counts.get(ch, 0) + 1
    return "".join(f"{n}{ch}" for ch, n in counts.items())

2 · Mean, median and mode — by hand

An analyst's favourite warm-up: "compute the average, the median and the most frequent value without NumPy". It checks three things at once — that you know what each statistic means, that you handle the edge cases, and that you know which one to trust.

Given
amounts = [120, 80, 340, 55, 80, 2000]
→
Answer
round(mean(amounts), 2) → 445.83
median(amounts) → 100.0
mode(amounts) → [80]
Mean: sum divided by count

The definition is the algorithm: add everything up, divide by how many there are. The only trap is the empty list — dividing by zero crashes, so return None first.

def mean(nums):
    if not nums:
        return None                   # an empty list has no mean (and avoids / 0)
    return sum(nums) / len(nums)
Median: the middle of the sorted data

Sort first — the median of unsorted data is meaningless. With an odd number of values there is one middle element. With an even number there are two, and the median is their average. The index of the middle is n // 2.

def median(nums):
    if not nums:
        return None
    s = sorted(nums)                  # the median only makes sense on sorted data
    n = len(s)
    mid = n // 2
    if n % 2 == 1:                    # odd length: one middle element
        return s[mid]
    return (s[mid - 1] + s[mid]) / 2  # even length: average of the two middles

def mode(nums):
    """All most frequent values, sorted (there can be several)."""
    if not nums:
        return []
    counts = {}
    for x in nums:
        counts[x] = counts.get(x, 0) + 1
    top = max(counts.values())
    return sorted(x for x, c in counts.items() if c == top)
Which one to trust: one large order of 2000 pulls the mean up to almost 446, while the median stays at 100 — closer to a typical order. With skewed data like revenue, report the median alongside the mean. Saying this unprompted is what turns a coding answer into an analyst's answer.
Where people slip: forgetting to sort before taking the median; using n / 2 instead of n // 2 (a float cannot be an index); forgetting the even-length case; and returning one mode when there are several.

3 · Sorting: when it helps and how to control it

Sorting is rarely the answer by itself — it is the step that makes the answer easy. After sorting, similar things stand next to each other: duplicates sit in a row, close values become neighbours, and the smallest and largest are at the two ends. That is what makes two pointers and "compare with the neighbour" work. The price is O(n log n), so it pays off when it removes an O(n²) search.

sorted() or .sort() — and the classic bug

sorted(x) returns a new sorted list and leaves x untouched. x.sort() sorts the list itself and returns None. So x = x.sort() silently replaces your data with None — one of the most frequent mistakes in live coding.

data = [3, 1, 2]
result = sorted(data)
print(result, data)    # a new list; data is unchanged

result = data.sort()
print(result, data)    # None — and data itself is now sorted
# output when run:[1, 2, 3] [3, 1, 2] None [1, 2, 3]
Sorting by several rules at once: the key

The key argument is a function that turns each element into "what to compare". If it returns a tuple, Python compares the first values, and only on a tie looks at the second. A minus sign flips a number into descending order. So key=lambda kv: (-kv[1], kv[0]) reads as: "most frequent first; on a tie — alphabetically".

If you are asked to write a sort yourself

Insertion sort is the easiest to explain, because it is how people sort cards in their hand. The left part is always sorted. Take the next card and slide it left past every bigger card until it fits. It is O(n²), so in real work you use sorted() — Python's built-in algorithm is O(n log n). But being able to state the rule "the left part stays sorted" is exactly what the interviewer is checking.

nums = [5, 2, 4, 6, 1, 3]
→

def insertion_sort(nums):
    nums = nums[:]
    for i in range(1, len(nums)):
        current = nums[i]
        j = i - 1
        while j >= 0 and nums[j] > current:   # shift bigger values one step right
            nums[j + 1] = nums[j]
            j -= 1
        nums[j + 1] = current                 # drop current into the gap
    return nums

4 · Two pointers and duplicates

Two indexes move through the data by a rule, instead of a loop inside a loop. Every step moves at least one pointer, so the whole walk takes at most n steps — O(n). Everything depends on the rule: which pointer moves, and why that move can never skip the right answer. If you can say that sentence out loud, you understand the solution.

Shape A · towards each other

One pointer at each end, moving inwards. Works on sorted data and on symmetric questions (palindromes, reversing). Take a sorted list and a target sum. If the sum of the two ends is too small, the left number cannot be part of any answer — even paired with the largest remaining number it falls short. So we drop it and move left. If the sum is too big, the same logic drops the right number.

Given
nums = [1, 3, 4, 6, 8, 11]
target = 10
→
Answer
two_sum_sorted(nums, target) → [2, 3]
def two_sum_sorted(nums, target):
    """Sorted list: positions of two numbers that add up to target (opposite pointers)."""
    left, right = 0, len(nums) - 1
    while left < right:
        total = nums[left] + nums[right]
        if total == target:
            return [left, right]
        if total < target:
            left += 1                 # need a bigger sum: only moving left can give one
        else:
            right -= 1                # need a smaller sum: only moving right can give one
    return []

Shape B · same direction, fast and slow

Both pointers start on the left. F (fast) reads every element. S (slow) marks where the "good" part of the array ends. When fast finds something worth keeping, it is copied to the slow position and slow moves on. This is how you clean an array in place without a second list: removing duplicates, moving zeroes to the end, compressing.

def remove_duplicates(nums):
    """Sorted list: keep unique values at the front, return how many."""
    if not nums:
        return 0
    slow = 0                          # last position of the unique part
    for fast in range(1, len(nums)):  # fast scans everything
        if nums[fast] != nums[slow]:
            slow += 1
            nums[slow] = nums[fast]
    return slow + 1

Removing duplicates: two different questions

Shape B above removes duplicates in place from a sorted array — that is a LeetCode-style constraint. The everyday interview version is simpler and more common: "return the list without duplicates". def dedup_keep_order(items):
    """[3, 1, 3, 2, 1] -> [3, 1, 2]: drop repeats, keep the first occurrence."""
    seen = set()                      # what we have already taken
    result = []
    for x in items:
        if x not in seen:
            seen.add(x)
            result.append(x)
    return result

Shape C · one pointer on each of two lists

When two sorted lists have to be combined or compared, give each its own pointer. At every step compare the two current elements, use the right one, and move only that pointer. Merging sorted lists, checking whether one string is a subsequence of another, and finding common elements all follow this shape.

    return i == len(s)

Complexity: what Big-O actually means

Big-O answers one question: when the input grows, how fast does the work grow? It does not measure seconds — those depend on the computer. It describes the shape of growth. O(n) means "twice the data, twice the work". O(n²) means "twice the data, four times the work".

The chart shows why this matters more than any micro-optimisation. On small inputs every approach is fast. As the data grows, O(n²) leaves the others behind — and that is the curve your interviewer wants you to avoid.

A real measurement, not a promise

Both functions below solve Two Sum. I timed them on arrays of growing length, on the worst case where no answer exists and every element must be checked. The numbers are measured, not modelled.

def two_sum_brute(nums, target):
    for i in range(len(nums)):
        for j in range(i + 1, len(nums)):   # every pair
            if nums[i] + nums[j] == target:
                return [i, j]
    return []

def two_sum(nums, target):
    seen = {}                          # value -> index
    for i, x in enumerate(nums):
        need = target - x
        if need in seen:
            return [seen[need], i]
        seen[x] = i
    return []
Look at the step from 2,000 to 4,000 elements: the input doubled, the nested loops became roughly four times slower, and the dictionary only twice as slow. That is O(n²) against O(n) — visible in real milliseconds.
Memory counts too. The fast solution stores up to n values in a dictionary — O(n) extra memory. That is the usual trade: spend memory to save time. Interviewers often ask "can you do it with O(1) memory?" — be ready to say what it would cost.

def count_letters(text):
    """'Hello, World!' -> '1h1e3l2o1w1r1d': ignore case, spaces and punctuation."""
    counts = {}
    for ch in text.lower():
        if ch.isalpha():              # skip everything that is not a letter
            counts[ch] = counts.get(ch, 0) + 1
    return "".join(f"{n}{ch}" for ch, n in counts.items())

            if s[lo] != s[hi]:
                return False

            hi -= 1

        right -= 1
    return True

On unsorted data you search by walking once and remembering the best so far — that is O(n), and you cannot do better. 1Two Sum
Arrays & hashingEasy#1 Open on LeetCode ↗
The task

Given a list of numbers and a target, return the positions of the two numbers that add up to the target. Exactly one such pair exists, and you may not use the same element twice.

nums = [3, 8, 11, 5, 4], target = 9 → [3, 4] # 5 + 4
The obvious approach

Check every pair with two nested loops. It works, but for n numbers that is about n²/2 comparisons — 50 million for 10,000 elements.

The key insight
For each number x we already know exactly which partner we need: target − x. So instead of searching for it, we remember every number we have passed in a dictionary and simply ask "have I seen my partner?" — an instant lookup.

    seen = {}                          # value -> index
    for i, x in enumerate(nums):
        need = target - x
        if need in seen:
            return [seen[need], i]
        seen[x] = i
    return []

Adding the number to seen before checking for its partner. With target 10 and the number 5, the code would pair 5 with itself.

The task

A string contains only brackets of three kinds. Decide whether every bracket is closed by the same kind, in the correct order.

Binary searchEasy#704 Open on LeetCode ↗
The task

Find the position of a value in a sorted list, or return −1 if it is not there.

    while left <= right:

        else:

def product_except_self(nums):
    n = len(nums)
    answer = [1] * n
    prefix = 1
    for i in range(n):                  # left-to-right: product of everything before i
        answer[i] = prefix
        prefix *= nums[i]
    suffix = 1
    for i in range(n - 1, -1, -1):      # right-to-left: times everything after i

        suffix *= nums[i]
    return answer

def three_sum(nums):
    nums = sorted(nums)
    res = []
    for i in range(len(nums) - 2):
        if i > 0 and nums[i] == nums[i - 1]:
            continue                       # skip duplicate anchors
        left, right = i + 1, len(nums) - 1
        while left < right:
            s = nums[i] + nums[left] + nums[right]
            if s < 0:
                left += 1
            elif s > 0:
                right -= 1
            else:
                res.append([nums[i], nums[left], nums[right]])
                left += 1
                right -= 1
                while left < right and nums[left] == nums[left - 1]:
                    left += 1

6Maximum Average Subarray I
Sliding windowEasy#643 Open on LeetCode ↗

Find the contiguous stretch of exactly k numbers with the highest average, and return that average.

nums = [1, 12, -5, -6, 50, 3], k = 4 → 12.75
Do not re-add k numbers for every window. When the window slides one step, add the new number and subtract the one that left.
def find_max_average(nums, k):
    window = sum(nums[:k])
    best = window
    for i in range(k, len(nums)):
        window += nums[i] - nums[i - k]
        best = max(best, window)
    return best / k
Why it works
Each slide costs two operations instead of k, so the whole scan is O(n) — the same trick as a 7-day rolling average.

7Daily Temperatures
StackMedium#739 Open on LeetCode ↗

For each day, return how many days you must wait for a warmer temperature. If it never gets warmer, return 0 for that day.

[73, 74, 75, 71, 69, 72, 76, 73] → [1, 1, 4, 2, 1, 1, 0, 0]
Keep a stack of days still waiting for a warmer one. When a warm day arrives, it resolves every colder day on top of the stack.
def daily_temperatures(temps):
    answer = [0] * len(temps)
    stack = []                          # indices of days still waiting
    for i, t in enumerate(temps):
        while stack and temps[stack[-1]] < t:
            j = stack.pop()
            answer[j] = i - j
        stack.append(i)
    return answer
Why it works
Each day is pushed once and popped once, so the total work is O(n) even though there is a loop inside a loop. This is the "monotonic stack" pattern.

StackMedium#155 Open on LeetCode ↗

Design a stack that supports push, pop, top, and returning the current minimum — every operation in constant time.

class MinStack:
    def __init__(self):
        self.items = []                 # pairs: (value, min so far)
    def push(self, x):
        current_min = min(x, self.items[-1][1]) if self.items else x
        self.items.append((x, current_min))
    def pop(self):
        self.items.pop()
    def top(self):
        return self.items[-1][0]
    def get_min(self):
        return self.items[-1][1]
Why it works
Each entry carries its own snapshot of the minimum, so popping automatically restores the previous minimum — no searching required.

A list of non-overlapping intervals is sorted by start. Insert a new interval, merging wherever needed, and keep the result sorted.

[[1,3], [6,9]] + [2,5] → [[1,5], [6,9]]
Three phases: copy everything that ends before the new one starts, merge everything that overlaps it, then copy the rest.
def insert_interval(intervals, new):
    res = []
    i, n = 0, len(intervals)
    while i < n and intervals[i][1] < new[0]:
        res.append(intervals[i]); i += 1
    start, end = new
    while i < n and intervals[i][0] <= end:
        start = min(start, intervals[i][0])
        end = max(end, intervals[i][1])
        i += 1
    res.append([start, end])
    res.extend(intervals[i:])
    return res
Why it works
Because the input is already sorted, a single pass is enough — no re-sorting, O(n).

    return removed

18Coin Change
Dynamic programmingMedium#322 Open on LeetCode ↗

Given coin denominations, find the fewest coins that make up an amount, or return −1 if it cannot be done.

Build a table: the fewest coins for every amount from 0 up. For each amount, try every coin as the last one.
def coin_change(coins, amount):
    INF = amount + 1
    dp = [0] + [INF] * amount
    for a in range(1, amount + 1):
        for c in coins:
            if c <= a:
                dp[a] = min(dp[a], dp[a - c] + 1)
    return dp[amount] if dp[amount] != INF else -1
Why it works
Greedy fails here — with coins [1, 3, 4] and amount 6 it picks 4+1+1, while 3+3 is better. Dynamic programming checks every option once and finds the true minimum.

How to practise so it sticks

Solving a hundred problems once teaches less than solving thirty properly. A few habits make the difference.

  • Learn the pattern, not the answer. After each problem, write one sentence: "this was a sliding window because…". That sentence is what you will recall at the interview.
  • Give yourself 25 minutes. If you are stuck after that, open the hint. Still stuck after 10 more — read the solution, then solve it again from scratch the next day.
  • Talk out loud. Practise explaining your reasoning as you go. At an interview, silent coding is the most common way to lose points you actually earned.
  • Revisit after a week. Spaced repetition beats volume. A problem you can still solve seven days later is a problem you have learnt.
  • Always state the complexity. Finish every solution by saying its time and memory cost. Interviewers expect it, and it forces you to check whether there is a faster way.
